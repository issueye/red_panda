# v0.1.1 Development Plan

Updated: 2026-07-09

This document defines the next development slice after the tagged v0.1.0 baseline.

v0.1.1 is a stabilization and design release. Its purpose is to keep the v0.1.0 local agent loop reproducible while preparing MCP stdio tools carefully enough that implementation can start in a later slice without disturbing Runtime/Gateway/Desktop boundaries.

## 1. Baseline

Authoritative baseline:

- Commit: `e223831`
- Tag: `v0.1.0`
- Release notes: `docs/17-v0.1.0-release-notes.md`
- Release gate: passed on 2026-07-09

Current stable architecture:

```text
Desktop(Wails v3 + React) <-> Gateway(Gin/GORM/SQLite no-cgo) <-> Agent Runtime(stdio JSON-RPC)
```

MCP stdio tools were intentionally excluded from v0.1.0. The next work must not jump straight into implementation before the design is written.

## 2. v0.1.1 Goal

v0.1.1 should deliver:

1. A scoped MCP stdio tools design document.
2. A stable implementation plan for MCP that preserves Runtime-owned tool execution and Gateway-owned state/projections.
3. Test fixtures or harness design for MCP stdout/stderr isolation, even if the MCP runtime is not implemented yet.
4. Release hygiene improvements for repeatable local builds and Gateway-backed tests.
5. No regression in the v0.1.0 release gate.

## 3. Non-Goals

Do not include these in v0.1.1:

- Full MCP stdio tools implementation.
- HTTP MCP transport.
- Plugin marketplace.
- Remote access hardening.
- Vector memory search.
- Broad Desktop UI redesign.
- Rewriting the existing ToolRunner before the MCP design is accepted.

## 5. MCP Design Requirements

The MCP stdio design must answer these questions before code starts:

1. Where MCP processes live.
   - Decision target: Agent Runtime owns MCP stdio child processes.
   - Gateway owns MCP config persistence and passes enabled configs to Runtime.
2. How MCP server config is represented.
   - Required fields: server name, command, args, env, cwd, enabled flag, timeout, tool allowlist, risk override.
3. How tools are named.
   - Proposed convention: `mcp__server__tool`.
   - Must be reversible for provider-facing OpenAI-compatible names.
4. How tools enter Runtime.
   - Built-in tools and MCP tools should share `AvailableTools`, policy evaluation, permission requests, and `tool_*` events.
5. How stdout/stderr isolation is enforced.
   - Runtime stdout to Gateway must remain JSON-RPC only.
   - MCP stdout must be read by an MCP protocol reader only.
   - MCP stderr must be drained to logs/ring buffer and never written to Runtime stdout.
   - Non-JSON MCP stdout is a protocol violation and should produce a failed MCP tool/server state.
6. How cancellation and timeout work.
   - Run cancellation must cancel active MCP calls.
   - Server shutdown must clean child processes.
7. How Gateway/Desktop observe MCP.
   - Reuse existing `tool_started`, `tool_output`, `tool_finished`, `tool_failed`, permission, and Activity timeline projections.
   - Add UI only after backend contract is stable.

## 9. Stop Rules

Pause before coding if:

- The MCP design would require Gateway to execute tool calls directly.
- MCP logs could reach Runtime stdout.
- MCP tool calls would bypass existing permission policy.
- MCP state would be invisible in tool audit or Activity timeline.
- A proposed Desktop UI requires a backend contract that is not designed yet.
- A test depends on arbitrary sleeps instead of real process/API state.

## 10. Exit Criteria

v0.1.1 is done when:

1. `docs/19-mcp-stdio-tools-design.md` exists and resolves the required design questions.
2. `docs/12-current-execution-plan.md` contains an ordered post-design MCP implementation queue.
3. `docs/10-development-status.md` and `README.md` describe v0.1.1 accurately.
4. `docs/20-v0.1.1-release-notes.md` exists.
5. The appropriate verification gate passes.
6. No MCP implementation is claimed unless it has actually been implemented and verified in a later scoped slice.
