# Goal 模式上下文共享方案:Goal Scratchpad(目标工作笔记)

## 核心问题(经代码验证)

当前 goal 模式在三个边界丢失上下文:

1. **段间(同 run 内)**:`carrySummarizedHistory` 只保留**尾部 6 条** tool 交换,每条截断到 500 字符,**早期工具结果全丢、assistant 推理文本全丢**(`runtime.go:666`、`goal_loop.go:13-14`)
2. **专家子代理**:子代理 `Session.Conversation = nil`、`GoalContext = nil`、`TodoContext = nil`(`subagent_tools.go:160,170-171`),**只拿到一句 task 文本**——完全看不到目标、分析、前期发现
3. **跨 run**:会话消息硬上限 200 条(`run.go:319`),超出即静默丢弃,**无自动摘要**

**关键架构事实(已验证)**:专家子代理进程通过 `newSubAgentProcessWithRequestHandler(..., r.callGateway)`(`runtime.go:117`)**继承了根代理的 Gateway RPC 管道**,且 `childParams.Session.ID` 保留。因此子代理**本可**调用 Gateway——只是被 `subagentRunDenylist`(`subagent_tools.go:23-40`)挡住了 `goal.*`/`todo.*`/`subagent.*`。一个**不在 denylist 里的新工具**天然可被子代理调用。

## 方案:Goal Scratchpad(持久化工作笔记)

在 Gateway SQLite 新增 `goal_notes` 表,作为 goal 范围内的**结构化、持久化、可检索的工作记忆**。根代理和专家子代理通过新的 `context.read/write/search` 工具(走现有 `callGateway` RPC)读写。笔记在段间、跨 run、根↔专家之间**共享同一份真相**,替代当前"task 文本里塞一切"的脆弱做法。

### 设计原则

- **复用现有 RPC 管道**:不新建连接,复用 `callGateway`(根)/继承的 `onRequest`(子)
- **不在 denylist 里的新工具名**:`context.*` 不与 `goal.*`/`todo.*`/`subagent.*` 冲突,子代理可调
- **Gateway 为唯一存储**:SQLite 表,崩溃/重启/跨 run 都在;Runtime 不持有副本
- **追加为主、覆盖为辅**:笔记默认追加(像日志),避免覆盖丢失;显式 `replace` 才覆盖
- **goal 范围 + kind 分类**:笔记绑 `goal_id`(必须)+ `session_id` + `kind`(finding/decision/risk/fact/handoff),便于按类检索

## 数据模型

### 新增表 `GoalNote`(`model/models.go`,沿用 Goal/AgentDefinition 约定)

```go
type GoalNote struct {
    ID        string `gorm:"primaryKey"`
    GoalID    string `gorm:"index;uniqueIndex:idx_goal_note_seq"`
    SessionID string `gorm:"index"`
    Seq       int    `gorm:"uniqueIndex:idx_goal_note_seq"`  // goal 内单调递增,定序
    Kind      string `gorm:"index"`                          // finding|decision|risk|fact|handoff
    Title     string
    Body      string `gorm:"type:text"`
    Phase     string `gorm:"index"`                          // 写入时的 pipeline_phase
    Source    string                                         // root|specialist:goal-implementer|user
    RunID     string `gorm:"index"`
    Pinned    bool   `gorm:"index"`                          // 高亮笔记(始终进 top-N)
    CreatedAt time.Time
    UpdatedAt time.Time
}
```
- `idx_goal_note_seq` 保证 `(goal_id, seq)` 唯一 → 幂等写入
- 无 `DeletedAt`:笔记可 `archived`(靠 Body/Kind 表达)或物理删;保持简单

### Migration(`infra/database/migrate.go`)
`AutoMigrate` 列表追加 `&model.GoalNote{}`(在 `&model.GoalSegment{}` 之后)。

## Protocol 层(`modules/protocol/methods/methods.go`)

新增方法常量与 DTO(完全沿用 `GoalToolExecute` 的形状):

```go
ContextToolExecute = "context.tool.execute"

type ContextToolExecuteParams struct {
    RunID, SessionID, WorkspaceRoot, ToolCallID, ToolName string

    Status string
    Output string

type GoalNoteDTO struct {
    ID, GoalID, Kind, Title, Body, Phase, Source, RunID string
    Seq, Pinned int
    CreatedAt, UpdatedAt string
}
```

## Gateway 层

### Repository(`repository/context.go`,新文件,镜像 `goal.go` 约定)
- `ContextRepository struct { db *gorm.DB }` + `NewContextRepository(db)`
- `Append(note model.GoalNote) (model.GoalNote, error)` — 分配 `seq`(goal 内 `MAX(seq)+1`,事务内),`time.Now().UTC()` 戳
- `Replace(goalID, kind, title, body, ...) (model.GoalNote, error)` — 按 `(goal_id, kind, title)` upsert
- `List(goalID string, opts ListOpts) ([]model.GoalNote, error)` — 支持 `kind`/`pinned`/`limit`(默认 50,上限 200)/`sinceSeq` 过滤,`ORDER BY pinned DESC, seq DESC`
- `Search(goalID, query string, limit int)` — SQLite `LIKE` 在 Title+Body 上模糊匹配(纯 Go SQLite,无外部依赖)
- `Get(goalID, noteID)`、`Delete(goalID, noteID)`
- 幂等:`Append` 用 `ToolCallID` 去重(传 `arguments.tool_call_id`,首次写入库,重复返回已存在)

### Repository wiring(`repository/set.go`)
`Set` 加 `Contexts ContextRepository`;`NewSet` 加 `Contexts: NewContextRepository(db)`

### Service(`service/context.go`,新文件,镜像 `GoalService.ExecuteRuntimeTool`)
```go
type ContextService struct { repos repository.Set }
func (s ContextService) ExecuteRuntimeTool(p methods.ContextToolExecuteParams) (methods.ContextToolExecuteResult, error)
```
dispatch 于 `ToolName`:`context.write`/`context.read`/`context.search`/`context.replace`/`context.delete`。
- 校验 `session_id` 存在、`goal_id` 存在且非终态(写操作)、长度上限(`goalMaxNoteBodyRune = 8000`、`goalMaxNoteTitleRune = 200`)
- **权限边界**:写操作要求 `run_id == goal.active_run_id` **或** source 以 `specialist:` 开头(子代理只能写,不能直接改 goal 状态)。读/搜对同 session 的任何 run 开放
- 输出 JSON:`{action, count, notes:[GoalNoteDTO]}`

### Service wiring(`service/set.go`)
`Set` 加 `Context ContextService`;`NewSet` 加 `Context: NewContextService(opts.Repos)`

### Dispatch(`app/app.go`)
在 `runtimeclient.New` 回调的 switch 加 `case methods.ContextToolExecute:`(在 `GoalToolExecute` 之后),unmarshal → `services.Context.ExecuteRuntimeTool(req)`。

## Runtime 层(`modules/agent/internal/runtime/`)

### 新工具定义(`tools.go`,加入 `AvailableTools()`)
| 工具 | 风险 | 参数 | 说明 |
| --- | --- | --- | --- |
| `context.read` | low | `goal_id`, `kind?`, `limit?`, `since_seq?` | 读取 goal 笔记(默认 pinned+最近) |
| `context.search` | low | `goal_id`, `query`, `limit?` | 在笔记 title+body 模糊搜索 |
| `context.write` | high | `goal_id`, `kind`, `title`, `body`, `pinned?` | 追加一条笔记 |
| `context.replace` | high | `goal_id`, `kind`, `title`, `body` | 按 (kind,title) 覆盖(upsert) |
| `context.delete` | high | `goal_id`, `note_id` | 删除一条 |

**关键**:`context.*` **不加入** `subagentRunDenylist`,因此专家子代理天然可调 `context.read`/`search`(读)和 `context.write`(写发现)。写权限由 Gateway service 的 source 检查把关。

### Dispatch(`tools.go` `RunWithContext`)
新增 `case "context.read"/"context.search"/"context.write"/"context.replace"/"context.delete":`,经一个新的 `ContextExecutor`(类型 `func(ctx, ContextToolExecuteParams) (ContextToolExecuteResult, error)`)调 Gateway,镜像现有 `GoalExecutor`/`TodoExecutor`/`MemoryExecutor` 模式。`ToolRunner.ContextExecutor` 字段在 `New()` 里绑为 `r.executeContextTool` → `r.callGateway(ctx, methods.ContextToolExecute, req)`。

### 段间自动注入(关键增益,`goal_loop.go`)
在 `runWithGoalLoop` 每段开头刷新上下文处(`goal_loop.go:263-269`),**新增**:拉取 goal 的 pinned/top-N 笔记,拼进 `GoalContext.Context` 或 `MemoryContext`:
```go
if notesCtx := r.goalNotesContextForRun(params.RunID); notesCtx != "" {
    // 追加到 params.Options.GoalContext.Context 末尾
}
```
这样**段 N+1 自动看到段 N 的关键发现**,无需模型手动 `context.read`。实现:`executeContextTool` 读 top-N(默认 pinned 全部 + 最近 10 条),Gateway 侧缓存或 Runtime 侧按 runID 缓存(可选,首版直接每次 RPC 读)。

### 专家子代理的"工作交接"(关键增益,`subagent_tools.go` / `goal_specialists.go`)
派发专家时(`applyGoalSpecialist`),在子代理 `MemoryContext.Context` 里**追加 goal 摘要 + 顶部笔记**,让专家一启动就知道目标与已知发现:
```go
// 在 applyGoalSpecialist 里(子代理 task 构造前)
brief := r.goalBriefForChild(parentGoalID)  // 同步读 objective + pinned notes
childParams.Options.MemoryContext.Context = roleBlock + budgetNote + "\n\n" + brief
```
专家返回报告后,根代理(或自动)**把报告写入** `context.write kind=handoff`,成为下一段/下一个专家的输入。

> 注:子代理调 `context.read`/`write` 时 `goal_id` 从哪来?子代理的 `GoalContext` 被 nil 了。解法:专家 task 文本里由根代理注入 `goal_id`(根代理知道),或 `MemoryContext.Context` 里带一行 `goal_id: xxx` 供专家在调 `context.read` 时引用。首版采用后者(根代理在 brief 里写明 goal_id)。

## 不做的事(明确边界)

- **不引入向量检索/嵌入**:用 SQLite `LIKE` 模糊匹配,零依赖,与现有 grep 风格一致。向量检索是后续可选
- **不动 `carrySummarizedK=6`**:段间历史压缩保持原样,scratchpad 是补充而非替代
- **不动 200 条消息上限**:scratchpad 是结构化补充,会话消息历史保持现状
- **不自动 LLM 摘要段**:首版用"模型主动 `context.write` + 自动注入 pinned/top-N"的确定性路径,避免额外 LLM 调用与不确定性
- **不给子代理开 goal.* 工具**:`context.*` 之外,goal 状态管理仍归根代理

## 风险

- **goal_id 传递给子代理**:靠 MemoryContext 文本注入,专家需从文本里解析 goal_id 调 `context.read`。可接受(模型按指令做);若不稳,备选是给子代理 ReplyParams 加一个非 nil 的 `GoalID`(只读 id,不给 GoalContext),更稳妥——首版用文本,实测后定
- **笔记膨胀**:靠 `limit`+`pinned` 控制;`List` 默认 top-50,`Context` 注入只用 pinned+最近 10
- **并发写**:多专家同时 `context.write` → `seq` 由事务内 `MAX(seq)+1` 分配,无冲突;`replace` 按 (kind,title) upsert 天然幂等
